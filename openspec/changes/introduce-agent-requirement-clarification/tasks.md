# Tasks

## 1. Server orchestration and context

- [ ] 1.1 Add one clarification-run service for sequential runs with at most one non-terminal clarification run occupying the derived sequential clarification slot per Requirement; `phase=awaiting_assignment` occupies it without a daemon/runtime, `phase=active` occupies it with an assigned non-terminal run, and only `phase=terminal` releases it. Reuse only an unassigned same-start attempt before daemon selection, return the public run projection, and atomically persist daemon pin, Requirement binding, repository IDs, immutable context, and `session.start` before dispatch when assigned, changing the run to `phase=active`, `status=starting` and acquiring the slot before `session.started`.
- [ ] 1.2 Assemble immutable Requirement snapshot, North-selected deterministic bounded persisted conversation excerpt, and enabled repository metadata through existing server DTO conversion; always retain `start_message_id`, use North-owned message-count/UTF-8-byte sizing, and remove checkout/credential/domain values from the wire input.
- [ ] 1.3 Define the latest-run session projection with public `run_id`, `start_message_id`, `phase` (`awaiting_assignment`, `active`, `terminal`), `status` (`starting`, `running`, `completed`, `unavailable`), cancellation intent, and safe timestamps; keep latest-run reads UI-only and never use them as implicit mutation identity; return `{ "session": null }` only before any clarification run exists, keep older runs as internal history, and do not add retry state, attempt count, budget, backoff, or final `Failed` policy.
- [ ] 1.4 Ensure any Draft → Discussing start transition uses the caller's `expected_state_version`; stale conflict creates no session command while preserving the already-persisted requester message.
- [ ] 1.5 Define and test North-owned deterministic context selection: canonical persisted order, fixed message-count and/or UTF-8-byte bound, oldest non-start truncation, mandatory `start_message_id`, identical replay/reconstruction, no provider/model tokenizer influence, and no provider relevance selection.

- [ ] 9.2 Prove an assigned `phase=active` run rejects a different start message both before and after `session.cancel` `command_ack`, rejects later-message dispatch after `cancel_requested=true`, creates no second run or `session.start` command, and retains the sequential clarification slot until terminal runtime projection.
- [ ] 9.3 Prove an unassigned `phase=awaiting_assignment`, `status=unavailable` run exposes `run_id` and `start_message_id`, concurrent retries with that same message reuse only that run with at most one assignment/`session.start`, concurrent retry of that message versus a different message never lets the different message replace it, and the different message conflicts until cancellation.

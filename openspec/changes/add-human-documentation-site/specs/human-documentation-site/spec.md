# Spec Delta

## Purpose

The human documentation site gives North users and contributors a navigable place to learn product workflows and development practices, while preserving the repository's structured knowledge as the canonical source for system facts.

## ADDED Requirements

### Requirement: Site exposes human documentation sections
The site MUST provide navigable user guidance, contributor guidance, and changelog pages.

#### Scenario: User finds product guidance
- **WHEN** a visitor opens the site navigation
- **THEN** the visitor can reach user guidance and read how North requirements move from clarification to human review

#### Scenario: Contributor finds development guidance
- **WHEN** a contributor opens the site navigation
- **THEN** the contributor can reach project setup and contribution guidance

### Requirement: Homepage orients visitors
The site homepage MUST explain North's purpose and provide direct links to user guidance, contributor guidance, and published release history.

#### Scenario: Visitor chooses a path
- **WHEN** a visitor opens the site homepage
- **THEN** the visitor sees North's purpose and can directly open the user guide, contributor guide, or changelog

### Requirement: Human guides preserve canonical knowledge ownership
Human-facing pages MUST be authored as site content, not generated by importing or copying the `docs/` knowledge tree. Pages that summarize product or architecture facts MUST link to their canonical source in `docs/` and MUST NOT define competing normative behavior.

#### Scenario: Product facts have canonical references
- **WHEN** a human-facing page explains product or architecture behavior
- **THEN** it links to the relevant canonical source document and does not replace that document as the source of truth

#### Scenario: Site content builds independently
- **WHEN** the documentation site is built from its own package directory
- **THEN** the build uses site-owned content and does not require importing `docs/` files

### Requirement: Changelog reports published history
The changelog MUST link to the repository's published release history and MUST NOT present proposals or unreleased work as published releases.

#### Scenario: Visitor checks release history
- **WHEN** a visitor opens the changelog page
- **THEN** the page links to the repository's GitHub Releases page as the published release source

### Requirement: Site is statically buildable
The documentation site MUST produce deployable static files without requiring the North application server or its database.

#### Scenario: Build without application services
- **WHEN** a contributor installs the site's locked dependencies and runs its production build
- **THEN** the build succeeds and emits static pages for the documented sections without starting North services
